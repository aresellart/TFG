# Observations (noticed, NOT fixed)

Nothing listed here was changed during the reorganisation. Paths are the new paths and line numbers are as of branch `reorganize`.

## Known before the reorganisation (reported by the author)

1. **`phase3b_diagnostic/finetune_diag_singledisc.py`** (was `endtoend/finetune_with_diagnostic_disc.py`) is the **single-discriminator** version. It writes to `attack_results_endtoend_diagfinetune_singledisc_test` (l.61), trains only 3 classes (`TEST_CLASSES = [0, 7, 13]`, l.58) and uses `LAMBDA_DIAG_TEST = 1.0` (l.56). The thesis' 96.8% result came from an earlier **two-discriminator** version (loss = attack + lambda_real·realism + lambda_diag·diag, lambda_diag = 0.3, all 16 classes). That version was overwritten and is not in git history; the author will add the recovered file separately. The file was renamed to `finetune_diag_singledisc.py` so the two versions cannot be confused.
   - Consistent with this, `results/attack_results_endtoend_diagfinetune_final/evaluation_diagfinetune.json` has `overall = 96.77`, but no script in the repo writes generators to `attack_results_endtoend_diagfinetune_final/` (read by `phase3b_diagnostic/evaluate_diagfinetune_final.py` l.36 and `figures/make_diagfinetune_grid.py` l.17).
   - `phase3b_diagnostic/check_diagfinetune_stamps.py` l.24 reads `attack_results_endtoend_diagfinetune_test/`, a third directory that no script in the repo writes either (presumably the two-disc test run).
2. **Fine-tuning and the diagnostic discriminator use the fixed-position generators.** `phase3b_diagnostic/finetune_diag_singledisc.py` l.116 and `phase3b_diagnostic/train_diagnostic_discriminator.py` l.60 load `G_*.pt` from `RESULTS_DIR` in `phase3_endtoend/config_endtoend.py` (l.8), which is `attack_results_endtoend` (fixed bottom-right), not `attack_results_endtoend_randpos`.
3. **`phase1_generative/vaegan/finetune_v3.py`** (lambda_adv = 0.1, lr 5e-5) saves `vae_gan_finetune_best.pt` (l.185), but every later script loads `vae_gan_best.pt` (the 300-epoch model from `train_v3.py`). Also `phase1_generative/vaegan/evaluate_v3.py` l.12 evaluates the *finetune* checkpoint, not the one used downstream.
4. **BatchNorm with batch size 1 in end-to-end training.** Generators are trained in `train()` mode with a single z per step (`phase3_endtoend/train_endtoend.py` l.96 and l.122; `train_endtoend_randpos.py` l.119 and l.130; same pattern in `finetune_diag_singledisc.py` l.120 and l.130) and evaluated in `eval()` mode (`evaluate_endtoend.py` l.63). So training uses per-sample batch statistics and evaluation uses running statistics.

## Noticed during the reorganisation

5. **`common/stamps_dataset.py` may not match the server copy.** It was `dataset.py` in the root: 1,280 bytes, 32 lines, CRLF line endings. Converted to LF it would be 1,248 bytes, not the 1,188 bytes of the server's `datasets_local/stamps_dataset.py`, so the *content* differs by about 60 bytes. Defaults in this copy: `image_size=64`, `num_workers=4`, `pin_memory=True`. Please diff it against the server copy.
6. **Root `config.py` is byte-identical to `phase1_generative/lowkl_vae/config.py`.** It is still imported as `import config` by `phase2_zopt/evaluate_attack.py`, `qualitative_results.py`, `visualize_results.py`, `attack/attack_random_z.py` and `attack/evaluate_random_z.py`. `phase2_zopt/attack.py` imports the same values through the other copy (see 7), so there are two sources for the same settings.
7. **`phase2_zopt/attack.py` l.15** imported `tfg_stamps.autoencoder.config`, which does not exist in this repo. As instructed, it now imports `phase1_generative.lowkl_vae.config` (same values). The same broken import, plus `tfg_stamps.autoencoder.utils` and `datasets.stamps_dataset` (the last one collides with the HuggingFace `datasets` package), was in `phase1_generative/lowkl_vae/{train,evaluate,generate}.py`; those were redirected the same way. These scripts have no `sys.path` line, so run them from the repo root with `python -m phase1_generative.lowkl_vae.train`.
8. **Mixed machines.** `phase2_zopt/attack.py`, `evaluate_attack.py`, `qualitative_results.py`, `common/build_correct_list.py`, `attack/attack_random_z.py`, `attack/evaluate_random_z.py` and the low-KL / high-KL configs use WSL laptop paths (`/mnt/c/Users/aress/...`). The GPU scripts use `/home/asellart/tfg_stamps`. `phase1_generative/vaegan/config_v3.py` uses the server path.
9. **`common/build_correct_list.py` l.93** writes `correct_images_1.0.json`, but every script reads `correct_images.json`. The committed file was presumably renamed by hand.
10. **`phase1_generative/lowkl_vae/train.py`**: lines 10–95 are an older copy of the whole script, commented out as a string literal. The live code starts at l.96 and repeats the imports.
11. **`phase1_generative/lowkl_vae/generate.py`**: `torch` is imported twice, `LATENT_DIM`/`IMAGE_SIZE` are hardcoded (l.10–11) and then `config.*` is used anyway, and the model is built and loaded twice (l.13–14 on cuda/cpu, then again on cpu at l.18–19).
12. **`phase2_zopt/qualitative_vaegan.py` l.26** reads `attack_results_vaegan_random_z/`, which is written by `attack/attack_vae_gan.py`, **not** by Method 3 (`attack_gpu_vaegan_random.py` writes `attack_results_gpu_vaegan_random/`). So `figures/qualitative_vaegan_random_z.pdf` shows stamps from the earlier VAE-GAN run (batch 64, 1000 it), not Method 3.
13. **`phase2_zopt/evaluate_vaegan.py` l.31–38**: `VARIANTS` currently contains only `gpu_vaegan_random`. The other four `results/evaluation_*.json` files were produced by earlier edits of this list, which are not recoverable from the file.
14. **Figures use hardcoded numbers instead of reading `results/`.**
    - `figures/plot_comparison_final.py` l.26–47: the per-class rates match `results/attack_results/evaluation_results_full.json` (CPU) and `results/evaluation_gpu_*.json` (rounded). But the hardcoded `"avg"` for "VAE-GAN encoded (GPU)" is **84.6**, while the mean of its own 16 rates (and of the JSON) is **80.9**. "VAE-GAN random z (GPU)" says 80.5, and the JSON mean is 80.25.
    - `figures/plot_scatter_comparison.py` l.19–24: its "VAE-GAN" series match `results/evaluation_vaegan_{encoded_stamp,random_z}.json` (the `attack_vae_gan.py` run), **not** the GPU Methods 2/3 used in `plot_comparison_final.py`. The two scatter figures (`comparison_scatter.pdf` and `scatter_comparison.pdf`) therefore show different VAE-GAN numbers.
15. **`ablations/ablation_size.py`** docstring (l.11) says the 64×64 result "should match the original 97.7%". `results/attack_results_endtoend/ablation_size.json` has `"_overall"` = 97.10 for 64×64, while `results/attack_results_endtoend/evaluation_endtoend.json` has `overall` = 97.69. This script pastes with its own `TF.resize` + normalisation (`paste_patch_size`, l.45–71) instead of `common.patch_utils.paste_patch`, which may explain the gap.
16. **`figures/make_interpolation_comparison_figure.py`**: the docstring says the inputs are `high_kl_interpolation.png` / `vae_gan_interpolation.png`, but the code (l.25–26) reads `interpolation_high_kl.png` / `interpolation_vae_gan.png`. No script in the repo writes either name.
17. **`figures/plot_comparison_final.py` l.9** adds the absolute server path `/home/asellart/tfg_stamps` to `sys.path`, so it only imports `models.*` when run on the server.
18. **Output locations.** Scripts still write their outputs (checkpoints, `G_*.pt`, JSONs, PNGs, PDFs) to the repo root or to root-level `attack_results_*/` folders. Those paths were not changed because the same folders hold the untracked checkpoints on the server. `results/` and `figures/` hold the copies that were committed. After re-running a script, copy its JSON/PDF into `results/` or `figures/` by hand.
19. **`attack/attack_vae_gan.py` l.37–38**: `VARIANTS = ["random_z"]`, with the comment "encoded_stamp is fully done", so it was edited between runs.
20. **`models/rvl-resnet50.model`** (98.6 MB) is committed directly to git, not through LFS. Not changed.
